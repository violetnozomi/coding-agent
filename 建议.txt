二、并行工具调用（高价值，半天）
这是你文档里自己列出的 TODO，也是和工业级系统最明显的差距。面试官几乎一定会问"你的工具是串行的，怎么优化"。与其停留在口头回答，不如直接做出来。
具体做法：
python# 核心改动：在 loop.py 的工具执行环节
import asyncio

async def _execute_tools_parallel(self, tool_calls):
    # 分类：读操作可以并行，写操作必须串行
    read_ops = [tc for tc in tool_calls if tc.name in READ_TOOLS]
    write_ops = [tc for tc in tool_calls if tc.name not in READ_TOOLS]

    # 并行执行所有读操作
    read_results = await asyncio.gather(
        *[self._execute_one(tc) for tc in read_ops]
    )

    # 串行执行写操作（保持事务语义）
    write_results = []
    for tc in write_ops:
        result = await self._execute_one(tc)
        write_results.append(result)

    return read_results + write_results
面试时你就能讲："我把工具执行分成读写两类，读操作用 asyncio.gather 并行，写操作保持串行以维护事务的原子性。这是一个读写分离的并发策略。"这个叙事比"我计划做并行"强十倍。

三、加一个你自己的设计创新（核心差异化，1 天）
现在你的项目和网上的 ReAct Agent 教程在架构上没有本质区别。你需要至少一个"这是我自己想的"的点。以下几个方向选一个做：
方向 A：自适应 Context 策略
不要用固定阈值做压缩，而是根据任务类型动态调整。比如在做代码重构时保留更多历史上下文（因为需要全局理解），在做简单文件创建时激进压缩。你可以设计一个简单的分类器（甚至用规则）来判断任务复杂度，然后选择不同的压缩策略。
方向 B：工具调用的置信度校验
LLM 返回的 tool call 参数经常有幻觉（比如编辑了一个不存在的函数）。你可以在 dispatch 之前加一层预校验：对 edit_file，先检查 old_text 是否存在且唯一；对 bash，做静态分析判断命令是否合理。把校验失败的信息直接喂回 LLM，让它自我纠正，而不消耗一次真正的工具执行。这个思路可以显著减少无效的 tool call 轮次。
方向 C：多模型路由
你文档里提到了 Model Router，这个做出来会很有料。核心逻辑不复杂——根据任务复杂度和上下文长度选模型。关键是你要有量化数据：在你的 benchmark 上对比不同路由策略的通过率和 token 成本，展示"同样通过率下成本降低了 XX%"。
