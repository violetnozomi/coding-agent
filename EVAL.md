# NZ-Coder Evaluation

## 1. Overview

NZ-Coder is a repository-level coding agent focused on reducing common failure modes in coding-agent tasks:

- slow codebase exploration,
- context bloat from large tool outputs,
- noisy or overly broad verification,
- risky edits without impact review,
- unstable small-project scaffolding from underspecified prompts.

The current evaluation harness is intentionally lightweight. It is meant to demonstrate engineering capability for local bugfix, small-feature, and Greenfield project-creation tasks, not to claim enterprise-grade autonomous development.

## 2. Evaluation Setup

- Model: configured by `MODEL_ID` for live runs; `dry-run` mode is available without network.
- Task count: the harness supports 10-20 local JSON tasks; this repo includes `examples/eval_tasks` and `examples/project_creation_tasks` starter sets.
- Repo types: local Python demo repos today; the runner supports arbitrary local repos under the workspace.
- Max turns: per task via `max_turns`.
- Success criteria:
  - repair tasks: configured verification commands pass after the run.
  - project-creation tasks: expected files exist and configured verification passes.

Run repair tasks:

```bash
python -m nz_coder.eval_runner --tasks examples/eval_tasks --limit 3
```

Run Greenfield tasks:

```bash
python -m nz_coder.eval_runner --tasks examples/project_creation_tasks --limit 3
```

Force dry-run:

```bash
python -m nz_coder.eval_runner --tasks examples/project_creation_tasks --limit 3 --mode dry-run
```

## 3. Metrics

The runner writes a `summary` object to JSON and a `## Summary` block to Markdown. It records:

- Success rate
- Partial success count
- Average turns
- Average tool calls
- Average diff chars
- Verification pass rate
- Max-turn failures
- No-diff failures
- Final agent status
- Last verification state
- Whether a repo stayed dirty after tracked rollback

Each run writes:

```text
eval/results/<timestamp>.json
eval/results/<timestamp>.md
```

## 4. Results Table

Example result format generated by the local eval runner:

| Task | Type | Tags | Status | Turns | Tool Calls | Diff Chars | Verification | Notes |
|---|---|---|---:|---:|---:|---:|---|---|
| fastapi_todo_api | project_creation | python, fastapi | partial | 0 | 0 | 0 | 0/2 passed | dry-run example |
| fix_empty_parser | repo_repair | python, bugfix | success | 5 | 5 | 412 | 2/2 passed | verification passed |

Dry-run mode is useful for validating task loading and result writing without a model; it intentionally does not apply patches.

## 5. Analysis

Modules that directly support evaluation quality:

- `smart_search`: reduces initial codebase exploration by ranking likely files from issue text and traceback.
- `read_symbol`: avoids reading entire Python files when the relevant class/function is known.
- `RuntimeState`: reminds the model about diff state, idle turns, task mode, and verification status.
- `VerificationPlanner`: recommends low-noise commands such as `py_compile`, exact pytest IDs, package-local Go checks, or configured JS/TS typecheck scripts.
- `ImpactAnalyzer`: summarizes risk, sensitive paths, affected files, likely tests, and final review notes.
- `RequirementAnalyzer` + `ProjectBlueprint`: stabilize Greenfield planning before file creation.
- `TemplateRegistry` + `write_files_batch`: make project scaffolding reproducible and transactional.
- `ChangeTracker` / `TransactionManager`: record edits and provide rollback for tracked file changes.

## 6. Limitations

- Python support is currently the most complete.
- TypeScript, Go, and Rust support are basic and command-driven.
- There is no Docker, VM, or OS-level sandbox.
- Verification quality depends on the target repository's tests and typecheck scripts.
- Greenfield mode is aimed at small local projects, not large production systems.
- The harness is not an enterprise unattended-agent evaluation platform.

## 7. Future Work

- TypeScript symbol indexing and caller lookup.
- Better related-test selection from imports and path ownership.
- Stronger template coverage for Node/TS services.
- Optional Docker or bubblewrap sandbox for live eval runs.
- Structured memory folding and cleanup policies.
